## Следующий этап: узкие воркеры
Разделить агента по ролям, по одной за раз, у каждой свой workflow и свой файл состояния:
- исследователь (чтение сети, заметки)
- публикатор (посты и ответы)
- хранитель памяти (факты, рефлексия, чистка)
- мастер инструментов (песочница, лаборатория)
- собеседник (ответы людям)
Цель: меньше токенов на задачу, сбой одной роли не валит остальных.

## Качество и доверие
- Проверка фактов по первоисточникам, цитаты-доказательства в исследованиях.
- Метрики: ответы людям, повторные собеседники, отказы проверяющего, расход лимитов. Публиковать и нулевые результаты.
- Идентичность: публичная страница и A2A-карточка поддерживаются в актуальном виде.
- Правила контакта: отвечаем тем, кто пишет сам; никаких массовых рассылок и давления; запрос «хватит» заканчивает контакт.

## 23.11: два внешних аудита, сверка с кодом
Применено (проверено по коду): docstring перед API_VERSION больше не переводит модуль в открытый режим (разбор настоящим парсером); новые модули в открытом режиме не устанавливаются; модули видят стандартные модули только на чтение, присваивание атрибутов чужим объектам запрещено (иначе можно было подменить json.loads для ядра); код модуля не длиннее 6000 символов, владельцу показывается целиком в сообщениях с SHA256, рецензент видит его тоже целиком; рецензия с неверным уровнем риска считается провалом; api.weekly с таймаутом; в Telegram проверяется отправитель (TG_OWNER_ID или личный чат), не только чат; личные сообщения (канал dm) не пишутся в публичный журнал.
Отклонено как неверное: перекрытие запусков (concurrency group без отмены ставит запуски в очередь), «нет кнопок» (аудит смотрел старую версию), «preflight не останавливает» (сделано намеренно, чтобы безобидный сбой не останавливал цепочку).
Отложено: persist-credentials: false в workflow (нужна осторожная проверка записи состояния); защита скалярных переменных в PART_GUARD (части пишет только владелец); формулировка в Хартии про изменение поведения и README про печать хешей (нужно твоё решение).
